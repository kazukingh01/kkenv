## Programming guidelines

<<<
以下の点について熟慮し、あなたがコーディングをする事を前提に、あなたが分かりやすいと感じる記述方法で、不足ない（冗長であっても良い）ガイドラインをまとめてほしい. 既存のプロジェクトがない場合は、pythonを前提にして良い. 既存のプロジェクトがある場合は、ソースコードを読んだ上でその言語に適用できる形でまとめてほしい.

- 関数や変数の命名は、それが何に類似性があるかを、語順の始まりからそのグループが明確にするような規約であること. 例えば、car_name, parts_name ではなく、name_car, name_parts といった具合である
- 処理が単純で、入れ子にならないようなシンプルなループ構造では、x などの単純な変数でループすること. 例) listwk = [str(x) for x in range(10)]
- コメントは必要最低限で良い. 基本的には関数名や変数名で何をしているかを読み取れるべきである. ただ、def main() の中は、処理のブロック単位で適切にコメントを記述するべきである.
- エラーハンドリングは必要最低限かつ小規模に使うこと. 全てを try catch で囲むような事をしてはならない
- 関数に対する長々としたコメントは基本的に必要ないが、関数名だけでは読み取れず表現しきれない複雑な処理の場合は、簡潔にコメントを記載すること
- ログは python においては logging.Formatter('%(asctime)s - %(name)s - %(funcName)s - %(levelname)s : %(message)s') とすること. それ以外のプログラミング言語においては、これと同等のものをフォーマットとすること.
- 表示形式について、" - " で区切られている必要はなく、情報として過不足なければ問題ない.
- ログのフォーマットにある name はファイル名ではなく、 module path や target 名となっても良い. funcName が表示できない場合は、無くても良い. 
- ログの時刻はUTCとする
- アプリケーションの内容にも依存するが、データ取得や処理の依存先においてグローバルとなる場合は、基本的に全てUTCを標準として扱う
- 外部ソースとのデータの読み書きを伴う場合は、その出力結果をログで簡潔に示すこと. 例）データ件数や、一部データ、dataframe の shape など
- ログは、コメントを代用できるものである. ある処理ブロックの開始時は、コメントの代わりにINFOログで処理の開始を記載して良い
- python に限るが、 DEBUG の使用は避ける（DEBUGを表示しないモードでも、内部的に処理が走り、その内容を表示するための処理で必要以上に重くなるため）
- for ループ内などの単位時間あたりに多くの処理が走るブロックに書くログは、DEBUGで書く
- ある一定以上の処理を伴う関数は、開始と終わりにINFOログを書く. 特別にログに表示したい引数（例えば、処理ロジックを分岐するような mode のような引数）が無ければ logging.info("START") と logging.info("END") だけで良い
- python の場合は、関数宣言の直後に assert で、引数のバリデーションを行う事. それ以外の言語でも、必要な場合はそのバリデーションを行うこと
- 新規に関数を定義する場合、必ず既存の関数を見直して流用できるかどうかを検討すること
- 新規に関数を定義する場合、本当にそのファイルに記載して良いか、Directory Layout を見直した上で検討すること
- 新規にファイルを作成する場合、本当にそのファイルが必要か、既存のファイルに関数を追加するだけで良いのはないか、について、Directory Layout を見直した上で検討すること. ファイル作成しても全体構造のシンプルさや最適化具合に問題が無い場合、新規にファイル作成して良い.
- コード改修は、常に共通化できるロジックを模索し、常に全体のコードや構造が最適化される事を検討すること
- テストコードは書かなくて良い
- データベースへの書き込みロジックを伴う場合は、データベース接続を伴うクラスに必ず dummy 接続を用意する
- データベースへの接続を伴うアプリケーションの場合は、データベースの接続情報は環境変数用のファイルを用意し、それを読み込むものとする
- ある実行スクリプトにデータベースへの書き込みロジックがある場合は、"--update" フラグ（default は false）を用意する
- ある実行スクリプトに、データベースからの読み込み処理がなく、書き込み処理のみがある場合は、"--update" フラグ が true の場合は dummy 接続となるように制御する（つまり instance は必ず dummy 接続）
- ある実行スクリプトに、データベースとの読み込み処理と書き込み処理の両方がある場合は、instance は通常の接続を行い、書き込みロジック個所で "--update" フラグにより分岐し、書き込みを回避できる分岐を必ず作成する（つまり instance は通常接続し read は実データベースとやり取りし、--update フラグは書き込みを制御する）
- あなたがテストやコマンドを実行する場合は、"--update" フラグをつけてはならない
- コード量は基本的に少ない方が良いが、処理の複雑さや可読性を考慮した場合、冗長的になっても良い
