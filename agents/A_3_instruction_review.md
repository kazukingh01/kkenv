# 前提条件/共通のルール

## NEVER

- この指示書を編集・削除するな
- 「→」は使用禁止
- 文末に「。」は使わない

## IMPORTANT

- 基本的に日本語での応答をお願いする
- 「→」ではなく、「->」で代用する
- 「。」ではなく、「. 」ピリオド＆半角スペース(文末ではなく、文中の場合)を代用する.

# 目的

@./AGENTS.md に従い、既存のコードをレビューし、"review.out"を完成せよ. レビューするだけで良く、実際の修正は伴ってはならない

# 方法

1. @./AGENTS.md と、そこに記述があるレビューに関連するファイルを全て読み込み、そしてそれを基本指針とする
2. @./review.out を新規作成する（既存のファイルがある場合は空にする）
3. "review.out" に、プログラムロジックが書かれたファイル(*.py, *.rs, *.sh など. docs や .env などは含まない ) を dir / filename の形式で列挙せよ
4. 「基本指針」に従って既存のコードをレビューし、"review.out" にレビュー結果を記載せよ. 但し以下の点に注意すること
  - "AGENTS.md" の内容と異なる点について、そしてその修正方法について、具体的な関数名や変数名を伴って記せ
  - その修正方法がコードベースで３行を超える場合、具体的なコードの修正方法については記述せず、文章による指示にてその修正方針を明確にして修正指示を記せ
  - 修正方針が明確に複数提案可能な時、「基本指針」の方針と照らし合わせて一致度が高い順に、第２案まで記述せよ
  - あるレビューについて、それがさらにブレークダウンして細分化したレビューが可能かを検討せよ
  - あるレビューは、それが１つのレビューである事が分かるような "review.out" の構造にすること
  - この "review.out" はあなたとは別のエージェントが運用する. そのエージェントに伝わる過不足ない表現で記述すること
  - ある１つのレビューは、その修正が完了したかどうかが分かるフラグを用意すること. デフォルトは未完了フラグである. 別のエージェントが対応し、それが完了フラグになるような運用を想定する
  - ある１つのレビューは、そのレビューがどういう内容に基づくかを適切にカテゴライズすること.
  - ある１つのレビューは、一意となるナンバリングをすること
  - 基本指針に従ってコードレビューした結果、修正するほどではないが、グレー・曖昧・疑問と感じた点についても記述せよ. その際、修正方針は記載しなくて良い
  - グレー・曖昧・疑問と感じた点について、"GRAY"のカテゴリーで記述せよ
  - "GRAY" の点について、基本指針が曖昧もしくは間違いである可能性があると判断した場合は、その旨も記載せよ
  - 以上を包括した "review.out" のフォーマットは以下をイメージする
    ```
    dir / filename
    - [ ] 001-CATEGORY A: XXXXX
    - [ ] 002-CATEGORY B: XXXXX
    ...
    - [ ] 0XX-CATEGORY A: XXXXX
    ...
    ```
