# 目的

「アプリケーション」を読み、「設計書雛形」に従って、@./DESIGN_XXX.md を完成させよ

## 留意事項

- "DESIGN_XXX.md" は以下の「アプリケーション」にある機能を実装するための設計書として機能する事を目指す
- "XXX" には「アプリケーション」の機能にマッチするシンプルな名前をあなたが命名せよ
- 設計書を作成するだけで、実装はしない
- 実装はあなたではない別のエージェントがその設計書を読んで追加されるものである
- 別のエージェントがその設計書を読む事を想定して、設計書には情報が過不足なく記載されるべきである
- 「アプリケーション」の内容はざっくりとしたものであり、それを元に、全体的に統一感のある最適化された設計書作成を、あなたが行う
- 完璧な設計書は目指さない. 曖昧な点についても、それが曖昧である事を明確にした上で設計を行い、実装時にフレキシブルに判断を促すよう設計する

## コンポーネント設計

<<<
- 設計全体について、どこまでを機能分割し、独立したコンポーネントとして機能するかを検討する
- コンポーネントとは、具体的な実態/操作を指す. 画面, DB, WebAPI, Cron, 機械学習モデル, 事前学習, CSV, Backup batch など
- ある実態の実現方法については記載しなくて良い. 例えば DBは クラウド/Docker/ホストインストールなどの実現方法が考えられるが、そこは重要ではない. ただし、そのDBがクライアントにあるかサーバにあるかは重要である
- I/F の細かな定義は書かなくて良い
- コンポーネントの名称（英語）は、以下の「コンポーネント相関図」と整合性を取ること
- コンポーネントごとに採用言語/フレームワーク/最低限採用しそうなライブラリを明記せよ
- 各コンポーネントの役割や機能のコメントを、以下の例のように記載する

例)
[Client]
- コンポーネントA: コンポーネントAの役割と機能. ただの実態(DBやファイルやモデル)なのか操作(WebAPIや学習スクリプト)か. 操作の場合どういったI/F方式でどのコンポーネントとやり取りするのか
- コンポーネントB: ...
...

[Server A]
- コンポーネント1: ...
...

[Server B]
...
