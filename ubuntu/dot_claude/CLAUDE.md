# Response style

- 質問には**まず明確な答え**を返す。前置き・図・段階的な解説は基本不要
- 補足は聞かれてから出す。聞かれていない背景・選択肢・対処案を先回りで並べない
- 短い質問には短く答える（1〜数文）。長い説明は明示的に求められたときだけ

# Git

## commit

- **ユーザーが明示的に指示しない限り、絶対に `git commit` するな** 
- 「コミットして」「commit して」等の明示的な依頼、または `/safe-commit` のような commit を目的とした skill が呼ばれたときのみ実行する。タスク完了時に勝手にコミットしない

## push

- `commit` 同様、勝手に `push` する事は禁止する。以下の例外を除く
- `/safe-commit` 実行後、その結果が問題なければ `push` も連続して実行しても良い

## Review

- ある PR に対して `/review` が実行された場合、指摘したレビューは全て通し番号で管理する事
- その PR に前回以前のレビュー結果があるかを確認し、ある場合は最後の通し番号を引き継いで管理すること

# Coding style

コーディング及び、設計・リファクタは以下の指針に従うこと

## A. 同型の処理は 1 箇所に置く

同じ形の処理を複数箇所へ写すと、修正はいずれ必ずどれか 1 つに届かない。「N 箇所を同時に直す事」とコメントで約束しても同期は保てない

- 写しを作らず関数 1 本にする。違いは引数で渡す
- 既に写しがあるなら、直すついでに 1 本化する。片方だけ直さない

## B. 共通化は「呼び出し側に判断が残らない」ところまでやる

処理だけを共通化し、戻り値の解釈を各呼び出し元に残すと、複製は消えずに **1 段上へ移動する**だけになる。実際、ループを共通化した次のラウンドで「戻り値の扱いが 4 箇所でばらばら」が指摘されたケースが過去にある

- 呼び出し側に同じ形の `if` が並ぶなら、その `if` ごと共通化の内側へ入れる
- 共通化の単位は「処理」ではなく「判断を含むひとまとまりの意味」

## C. コードのコメントについて

基本的にコメントは書かなくてよい。コードが真実であり、その可読性がコメントの代わりとなる。明確で実態にそくした関数名や変数名を定義し、またそれに倣っていないものは修正の対象である

- コメントに書くのは**コードから読めない理由**だけ。そのロジックに背景があり、一見シンプルではなく共通化もされていないレビューで指摘されそうなコードには、コメントでその旨を記述しても良い

## D. テストは「落ちる事」を確かめてから信じる

「緑だが実は何もテストできていなかった」に事象が繰り返し出た経験がある。それらは条件が常に真、セレクタが別の要素に当たる、対象が skip されている、などが理由であり検証の条件が整っていなかったのである

- 追加した検証は、対象をわざと壊して**赤になる事を一度実測する**
- 実行対象から外れる条件 (skip・環境変数) は、外れた事が分かるように出す
- 壊す対象は「修正前の版」に戻す。**修正をコミット済みなら 1 つ前の版に戻す事**
  (コミット後の最新版に戻しても修正が入ったままで、変異テストが成立しない)

## E. 失敗を無言にしない

握り潰し・無言の早期 return・無言のフォールバックが繰り返し指摘された。利用者にも次の実装者にも、失敗した事実が残らない

- 失敗は必ずどこかに出す (利用者への表示、またはログ)
- 「一部だけ成功」は、何が成功して何が失敗したかを伝える

## F. 修正を入れる前の確認

- 同じ形が他の箇所にもないか
- 呼び出し側に新しい判断を足していないか
- その修正と矛盾する記述を残していないか
- 足した検証は本当に落ちるか

## G. 書き込み・トランザクションの集約

同じテーブルへの書き込みが分散されたり、ある機能の処理でトランザクションが増えるのは、データパターンの肥大化につながり、テストやレビューを複雑にする

- 可能な限り、ある特定の機能における INSERT / UPDATE は共通的な関数として集約され、データパターン（特定のカラムが null やそうではないパターンなど）は関数内で整理され、レコードとして残るパターンは極力少なくするべきである
- 同様に、データの変更を伴うトランザクションが複数に及ぶこともデータパターンを複雑にするため、トランザクションがまとまるものは可能な限り１連のトランザクションとして処理されること
- 全体として、INSERT / UPDATE が走る共通関数は最低限の数を保ち、かつ常に関数を減らす事ができるかを検討すること
