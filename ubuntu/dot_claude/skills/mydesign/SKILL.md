# My Design

issue を読み、コードベースを調査した上で設計書の骨子を書き、issue に投稿するスキル。

**コードは変更しない。コミット・push もしない。** 成果物は issue 上の設計書のみ。

---

## Step 1: 対象 issue の取得

1. `$ARGUMENTS` から issue 番号を取る (`#123` / `123` のどちらも可)。無ければ番号を尋ねて終了する
2. issue を **全件・末尾まで** 取得する (`head` で切らない)

```bash
gh issue view <番号> --json number,title,body,url,comments > <scratchpad>/issue-<番号>.json
```

3. 投稿先を決める:

| issue の状態 | 投稿先 |
|---|---|
| 本文に内容がある (空白・テンプレートの見出しのみではない) | **コメント返信** (`gh issue comment`) |
| タイトルしか無い (本文が空、または空白のみ) | **本文** (`gh issue edit --body-file`) |

4. 既に本スキルが投稿した設計 (`## 設計 (mydesign)` で始まるコメント or 本文) があれば、新規投稿ではなく **その投稿を上書き** する (Step 5 参照)。既存の設計を読み、issue 側で追加されたユーザーのコメント (回答・方針変更) を今回の設計に反映する

---

## Step 2: 調査

設計を書く前に、issue の内容に関係するコードを実際に読む。推測で書かない。

- 関連するモジュール・関数・テーブル・設定・テストを特定し、現状の構造と制約を把握する
- 対象リポジトリの `CLAUDE.md` (階層下のものも含む) を読み、規約を設計の前提に組み込む
- 既存の同種処理があれば、それに倣うか・1 本化するかを設計の論点にする (同型の処理を増やさない)
- 調査範囲が広い場合は `Agent` (Explore) に委ね、自分は結論だけを受け取る

---

## Step 3: 設計書の下書き

`<scratchpad>/issue-<番号>-design.md` に以下の構成で書く。各節の **書き方・粒度・構造は自分で決める** が、節の順序と見出しは固定する。

```markdown
## 設計 (mydesign)

### キーポイント
- <設計の核となる判断を箇条書き。各 1〜2 行>

### 設計内容
<具体的な設計。構造は内容に合わせて自由に決める>
<例: 変更対象ファイルと役割、データ構造・スキーマ、処理フロー、インターフェース (関数シグネチャ・API・CLI 引数)、エラー時の挙動、テスト方針、変更しない事 (スコープ外)>

### issue に書かれていないが AI 側で判断した事項
- <issue からは読み取れず、調査結果や慣習から自分で決めた内容。何を・なぜそう決めたかを 1 行ずつ>

### ユーザーに決めてほしい事・確認事項
- <判断が分かれる点、仕様として確定していない点、影響が大きく独断できない点。選択肢があれば併記し、自分の推奨を 1 つ示す>
```

書くときの指針:

- 「設計内容」は、変更対象のファイル・関数名を **実在するパス・名前** で書く (Step 2 で確認したもの)。新規に作るものは新規と明記する
- 「AI 側で判断した事項」と「確認事項」の線引き: 自分の判断に 80% 以上自信があり、違っていても修正が安価なら前者。それ以外は後者
- 失敗時の挙動 (エラーをどう出すか) を設計に含める。無言の握り潰し・無言のフォールバックを設計しない
- 書き込み処理を含む設計では、INSERT / UPDATE を担う関数を最低限の数に集約し、トランザクション境界を明記する

---

## Step 4: セルフレビュー (投稿前に必ず行う)

下書きを **「この設計書だけを渡された別のエージェントが、issue もこの会話も見ずにイチから実装できるか」** の観点で読み直す。

確認項目:

| 観点 | 確認内容 |
|---|---|
| 自己完結 | issue 本文や会話の文脈を前提にしていないか。前提は設計書内に書かれているか |
| 具体性 | 「適切に」「必要に応じて」など実装者が判断を迫られる曖昧語が残っていないか。残っているなら決めて書くか、確認事項へ移す |
| 実在性 | 挙げたファイル・関数・テーブルは実在するか (新規なら新規と書いてあるか)。パスは正確か |
| 完結性 | 入口 (どこから呼ばれるか) から出口 (結果がどう使われるか) まで繋がっているか。抜けた工程がないか |
| 境界 | 正常系だけでなく、エラー・空入力・既存データとの整合など境界条件の扱いが書かれているか |
| 検証可能性 | 実装者が「できた」と判断できる基準 (テスト方針・確認手順) があるか |
| 矛盾 | キーポイント・設計内容・判断事項・確認事項の間で食い違いがないか |

見つかった問題は **下書きファイルを直接編集して直す**。「レビュー結果」のような節を追記しない。レビュー前の版は残さない。

修正が大きい場合 (節の構成が変わる・判断事項が確認事項へ移る等) は、修正後にもう一度この表で読み直す。

---

## Step 5: issue への投稿

Step 1 で決めた投稿先に、セルフレビュー済みの下書きを投稿する。

```bash
# コメント返信 (本文に内容がある場合)
gh issue comment <番号> --body-file <scratchpad>/issue-<番号>-design.md

# 本文へ記載 (タイトルしか無い場合)
gh issue edit <番号> --body-file <scratchpad>/issue-<番号>-design.md
```

既存の設計投稿を上書きする場合:

```bash
# コメントの上書き
gh api -X PATCH repos/{owner}/{repo}/issues/comments/<comment_id> -F body=@<scratchpad>/issue-<番号>-design.md

# 本文の上書き
gh issue edit <番号> --body-file <scratchpad>/issue-<番号>-design.md
```

投稿後、URL を `gh issue view <番号> --json url` または API の応答から取得する。

---

## Step 6: 完了報告

以下を報告する:

- 投稿先 (コメント / 本文) とその URL
- キーポイントの要約 (箇条書き 3〜5 行)
- ユーザーに決めてほしい事・確認事項の一覧 (issue と同じ内容。ユーザーが issue を開かずに回答できるように)
- セルフレビューで修正した点の要約 (1〜3 行)
