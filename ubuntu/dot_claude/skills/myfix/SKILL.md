# My Fix

`/myreview` が投稿したレビュー指摘に対し、ユーザーの返信コメントに従って対応するスキル。

**コミット・push はしない。** 対応後の commit は `/safe-commit` またはユーザーの明示指示のみ。

---

## Step 1: 対象 PR と最新コメントの特定

1. `$ARGUMENTS` に PR 番号があればそれを使う。無ければ `gh pr view --json number,url` で現在のブランチから特定する
2. PR のコメントを **全件・末尾まで** 取得する (`head` で切らない)

```bash
gh api repos/{owner}/{repo}/issues/<PR番号>/comments --paginate > <scratchpad>/pr-<PR番号>-comments.json
```

3. 以下を特定する:
   - **対象レビュー**: 最後に投稿されたレビューコメント (`## レビュー (第 R ラウンド: #a〜#b)` 形式)
   - **ユーザーの最新コメント**: 対象レビューより後に投稿された、ユーザー本人のコメント。複数あれば全て読み、番号ごとの指示として統合する
4. 対象レビューより後にユーザーのコメントが無い場合は、その旨を伝えて終了する (指示なしでは対応を始めない)

---

## Step 2: 指摘の妥当性検証 (対応前に必ず行う)

対象レビューの **全指摘 (#a〜#b)** について、対応に着手する前にコードと照合する。ユーザーの指示があるものも例外にしない。

各番号について記録する:

| 項目 | 内容 |
|---|---|
| 事実 | 指摘の通りのコードになっているか (`git show` / 該当行の引用で根拠を残す) |
| 影響 | 実際に起きる失敗シナリオがあるか |
| 判定 | **バグ** / **仕様の可能性あり** / **事実誤認** |

- **事実誤認** と判断したものは、指示の有無に関わらず修正せず、根拠付きで Step 5 の報告に載せる
- 「仕様の可能性」の目安: 既存テストがその挙動を固定している、同じ形が意図的に複数箇所にある、コード中のコメントや過去 PR のコメントで判断済みの痕跡がある、挙動を変えると利用者に見える差が出る

---

## Step 3: 番号ごとの対応方針の決定

### 3-a. ユーザーが番号に言及している場合

指示の語彙で行動を区別する:

| 指示 | 行動 |
|---|---|
| 「修正して」 | 実装する (Step 2 で事実誤認なら修正せず報告) |
| 「検討して (必要であれば) 修正して」 | 要否は任されている。Step 2 の判定に従う |
| 「確認して」「これってどんな状況?」 | 調査と回答が成果物。**コードは変えない** (安い修正でも提案に留める) |
| 「不問とする」「仕様」 | 修正しない。「コメント書いておいて」があればコード側へ `PR #<番号> レビュー #N` を前置した判断コメントを固定する |

### 3-b. ユーザーが番号に言及していない場合

Step 2 の判定で自分で決める:

| 判定 | 行動 |
|---|---|
| 明らかにバグ (仕様の可能性 10% 未満) | 修正する |
| 仕様の可能性が 10% 以上 | **修正を開始しない。** Step 4 で方針をまとめて尋ねる |
| 事実誤認 | 修正せず、根拠付きで報告する |

---

## Step 4: 方針確認 (該当があれば、修正着手の前に)

3-b で「仕様の可能性 10% 以上」となった番号が 1 つでもあれば、**修正に着手する前に** `AskUserQuestion` でまとめて尋ねる。番号ごとに:

- 指摘の要約
- 仕様と考えられる根拠 (Step 2 の記録)
- 選択肢: 修正する / 仕様として不問 (コメント固定するか) / 保留

明らかにバグの番号の修正は、この確認と独立に進めてよい。

---

## Step 5: 対応の実施

修正する番号について、以下を守る:

- **同じ形が他にもないか** を先に確認し、あれば 1 本化する (片方だけ直さない)
- 呼び出し側に新しい判断を足さない
- 修正と矛盾する記述 (コメント・テスト・ドキュメント) を残さない
- 失敗を無言にしない (握り潰し・無言の早期 return・無言のフォールバックを作らない)

### テストを直す・足す場合

追加・変更した検証は **赤になる事を一度実測** してから信じる:

1. 変異前に対象ファイルを scratchpad へ `cp` でバックアップする (`git restore` は未コミットの修正ごと消すので使わない)
2. 修正前の挙動に戻す / 本物の assert を消す、で赤を確認する
3. `cp` で戻し、`diff -q` で復元を確認してから緑を報告する

対応が終わったら、変更したファイルのテスト・lint・型検査を実行する。

---

## Step 6: 完了報告と PR への返信

番号ごとに結果をまとめ、`gh pr comment` で PR に 1 本のコメントとして返信する。

```markdown
## 対応結果 (第 R ラウンド: #a〜#b)

| No. | 判定 | 対応 | 備考 |
|---|---|---|---|
| #a | バグ | 修正 (file:line) | ... |
| #a+1 | 仕様 | 不問・コメント固定 | ... |
| #a+2 | 事実誤認 | 未対応 | 根拠: ... |
| #a+3 | 要確認 | 方針待ち | 質問: ... |

### 確認事項への回答
- #x: <調査結果>

### 検証
- 実行したテスト / lint と結果
- 変異テストで赤を実測した検証: <対象と結果>
```

ターミナルにも同じ要約と、**未コミットである事** を明示する。
